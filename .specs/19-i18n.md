# 19 — Internacionalização da UI (i18n)
> Status: proposta · Esforço: 🟡 (mecânico, mas amplo — muitos arquivos) · Impacto: Médio/Alto se houver ambição de público fora do Brasil; baixo se o público-alvo for só pt-BR · Depende de: nada; sinergia com spec 20 (idioma da transcrição) — idioma da UI ≠ idioma do conteúdo

## Problema
A UI é 100% pt-BR com strings hardcoded e **misturadas com inglês** de forma inconsistente — botões em inglês ("Transcribe", "Generate Analysis", "Run Again", "Export Options", "Save to Folder") convivem com textos em português ("Apagar sessão", "Nenhuma fala detectada"). Não há infraestrutura de tradução. Para suportar outros idiomas (ou só padronizar pt-BR de verdade) é preciso extrair as strings.

## Como está hoje
- **Sem nenhuma lib de i18n** nas dependências (`apps/gui/package.json` — não há `react-i18next`/`i18next`/`lingui`; deps são clsx, date-fns, framer-motion, lucide-react, react, react-dom, react-markdown, zustand).
- Strings literais espalhadas pelos componentes. Exemplos concretos em `apps/gui/src/features/sessions/SessionDetailPage.tsx`:
  - Abas hardcoded em inglês: `const tabs = ["Transcript", "Analysis", "Export"]` (`SessionDetailPage.tsx:68`).
  - Mistura PT/EN: `"No transcript yet"` (`:156`), `"Transcribing..."` / `"Transcribe"` (`:163`), `"Nenhum áudio capturado nesta sessão."` (`:167`), `"Nenhuma fala detectada nesta gravação"` (`:180`), `"Generate Analysis"` (`:556`), `"Run Again"` (`:608`), `"Export Options"` (`:667`), `"Save to Folder"` (`:688`), `title="Apagar sessão"` (`:98`).
  - Modal de confirmação em PT inteiro (`:106-108`).
- Em `RecordingPage.tsx`: `"Recording from {device}"` (`RecordingPage.tsx:101`), `"{chunks} chunks saved"` (`:105`), `"Click to stop recording"` (`:161`), `title="Mutar áudio do sistema"` (`:121`), `title="Mutar microfone"` (`:150`).
- Outros arquivos com strings: `apps/gui/src/features/settings/SettingsPage.tsx` (16KB), `TemplatesPage.tsx`, `dashboard/`, `navigation/`, `analysis/`, `transcription/`, `export/`, e os componentes em `apps/gui/src/shared/ui/` (`Badge.tsx`, `ConfirmModal.tsx`, etc.).
- **Datas**: `date-fns` já é dependência (`apps/gui/package.json`) — provavelmente em `apps/gui/src/shared/lib/format.ts` (formatadores `formatDuration`/`formatTimestamp` usados em `SessionDetailPage.tsx:4`); locale de data precisa entrar no escopo do i18n.
- **Prompts dos templates são pt-BR e estão no CORE, não na UI**: `ANALYSIS_SYSTEM_PROMPT` força "SEMPRE responda em português brasileiro" (`packages/core/src/ports/analyzer.ts:11`); templates builtin são 100% PT (`packages/core/src/templates/meeting-summary.ts`, `action-items.ts`, `videoaula-insana.ts`). Isso **não é UI** — é conteúdo gerado pelo LLM (ver decisão abaixo).

## O que precisa ser feito
1. Adotar uma lib de i18n leve e extrair as strings da UI para arquivos de locale.
2. Criar `pt-BR` (default, fonte da verdade) e ao menos `en` como segundo locale.
3. Seletor de idioma da UI (Settings) com persistência.
4. Padronizar o que hoje está em inglês (oportunidade de limpeza junto da extração).
5. Definir política para os prompts dos templates (idioma da saída do LLM).

## Como implementar

### 1. Lib
Recomendo **`react-i18next` + `i18next`** (padrão de mercado, interpolação `{{var}}`, plural, lazy load de locales). Alternativa mais leve sem dependência: um `LanguageContext` + dicionário `Record<string, string>` próprio (zero deps, mas reimplementa plural/interpolação à mão). Dado o volume de strings, `react-i18next` paga o custo. Adicionar a `apps/gui/package.json` deps: `i18next`, `react-i18next`.

### 2. Estrutura de locales
```
apps/gui/src/i18n/
├── index.ts            # init do i18next + detecção
├── locales/
│   ├── pt-BR.json
│   └── en.json
```
`index.ts`:
```ts
import i18n from "i18next";
import { initReactI18next } from "react-i18next";
import ptBR from "./locales/pt-BR.json";
import en from "./locales/en.json";

i18n.use(initReactI18next).init({
	resources: { "pt-BR": { translation: ptBR }, en: { translation: en } },
	lng: localStorage.getItem("ui-lang") ?? "pt-BR",
	fallbackLng: "pt-BR",
	interpolation: { escapeValue: false },
});
export default i18n;
```
Importar em `apps/gui/src/main.tsx` (antes de renderizar o `App`).

Chaves por feature, ex. `pt-BR.json`:
```json
{
	"session": {
		"tabs": { "transcript": "Transcrição", "analysis": "Análise", "export": "Exportar" },
		"noTranscript": "Nenhuma transcrição ainda",
		"transcribe": "Transcrever",
		"transcribing": "Transcrevendo...",
		"deleteSession": "Apagar sessão"
	},
	"recording": {
		"from": "Gravando de {{device}}",
		"chunksSaved": "{{count}} trecho salvo",
		"chunksSaved_other": "{{count}} trechos salvos",
		"clickToStop": "Clique para parar a gravação"
	}
}
```

### 3. Migração dos componentes
Trocar literais por `t("...")` via hook `useTranslation`:
```tsx
const { t } = useTranslation();
const tabs = [t("session.tabs.transcript"), t("session.tabs.analysis"), t("session.tabs.export")]; // SessionDetailPage.tsx:68
// ...
{loading ? t("session.transcribing") : t("session.transcribe")} // SessionDetailPage.tsx:163
```
Migrar arquivo a arquivo: `features/sessions/`, `features/recording/`, `features/settings/`, `features/dashboard/`, `features/navigation/`, `features/analysis/`, `features/transcription/`, `features/export/`, e `shared/ui/`. Datas: passar `locale` do `date-fns` (ex.: `ptBR`/`enUS`) conforme idioma ativo em `shared/lib/format.ts`.

### 4. Seletor de idioma (Settings)
Em `SettingsPage.tsx`, um `<select>` que chama `i18n.changeLanguage(lng)` e grava `localStorage.setItem("ui-lang", lng)`. Não precisa de endpoint no server (preferência puramente client-side). Seguir o padrão visual dos selects já usados (ex.: `SessionDetailPage.tsx:538-548`).

### 5. Prompts dos templates (decisão de escopo)
Os prompts em `packages/core/src/templates/*` e o `ANALYSIS_SYSTEM_PROMPT` (`analyzer.ts:11`) controlam o **idioma do conteúdo gerado**, não da UI. Opções:
- **(v1, recomendado)** Manter i18n só para a **chrome** (botões, labels, mensagens). Templates continuam pt-BR. Usuário entende a interface em EN mas o resumo sai em PT.
- **(v2)** Tornar o idioma de saída configurável: remover o "SEMPRE responda em português" fixo de `analyzer.ts:11` e injetar o idioma via `extraPrompt` (já suportado — `analysis.service.ts:16-18,33-37`; concatenado em `groq-llm.ts:22-24` e `ollama.ts:22-24`). Isso é melhor tratado na **spec 20** (tradução/idioma do conteúdo). Deixar fora desta spec para não acoplar UI a LLM.

## Plano de testes
- **Automatizado**: lint que detecte literais JSX restantes (regex/`eslint-plugin-i18next` ou um script `grep` de strings em JSX). Garantir que toda chave de `pt-BR.json` existe em `en.json` (teste de paridade de chaves).
- **Visual/manual**: trocar idioma em Settings → toda a UI muda sem reload; recarregar a página → idioma persiste (localStorage). Datas no locale certo. Playwright MCP em `:1420`: snapshot em PT e EN, comparar que `data-testid`s não mudaram.
- **Regressão**: confirmar que `data-testid`/`aria-label` usados em testes (ex.: `stop-recording-button`, `session-back-button`) **não** foram traduzidos — só o texto visível.

## Riscos / decisões em aberto
- **Esforço amplo**: dezenas de strings em ~8 features + `shared/ui`. Risco de cobertura parcial — fazer por feature e marcar progresso.
- **`aria-label`/`title` vs `data-testid`**: traduzir os primeiros, nunca os segundos (testes dependem deles — ver `CLAUDE.md` "Key controls carry data-testid").
- **Plural/gênero em PT**: i18next cobre plural; gênero ("salvo/salva") exige chaves separadas.
- **Vale a pena agora?**: o produto é descrito como pt-BR-first (memory: "UI 100% em pt-BR"). Talvez a v1 seja só **padronizar tudo para pt-BR** (eliminar o inglês solto) e deixar o EN para depois — a extração de strings habilita ambos.
- **Bundle**: locales aumentam o JS; lazy-load por idioma se crescer.
